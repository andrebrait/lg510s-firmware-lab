## 5. Required corrections / sharpenings (doc line → finding → binary proof)

1. `docs/board4-investigation.md:101` and `:95` ("does not supply a verified partition boundary map", "static partition names only; no live map"): the kernel **does** carry the vendor's static boundary table immediately after the name array: vmlinux.bin 0x455530 = `00800000` (8 MiB) then 8 (offset,size) pairs, 0x455574 = `01000000` (16 MiB) then pairs, then 32 MiB. The 16 MiB row is corroborated by the env CRC at 0xe0000/64 KiB, JFFS2 magics at 0x100000/0x200000/0xf00000 and the image at 0x300000. Still static (not `/proc/mtd`), but it is a map, and the carved JFFS2 ranges *do* match CFG/LOG/OEMINFO one-to-one. Consequence if ignored: unnecessary refusal to reason about env/key areas; consequence if over-trusted: none beyond what the 7 magics already prove.
2. `docs/board4-investigation.md:106-109` ("conflicting evidence … do not prove that tftpboot; bootm is available"): not conflicting. Command table (proof `scratch/uboot_cmdtable.txt`): `tftpboot`→0x83f05530 (`li a0,3; j netboot_common 0x83f05254`), `bootp`→proto 0, `bootm`→0x83f03394 (full do_bootm, strings "Automatic boot of image at addr", "ERROR: booting os '%s' (%d) is not supported"), `go`→0x83f026e4, `loady/loadb`→0x83f04140, `loads`, `md/mw/cp/cmp/crc32/mtest`, `sf`, `erase/protect`, `saveenv`. "bootm command is not supported!" (0x83fc0078) is printed by **boota** at 0x83f02900 only if `find_cmd("bootm")` returns NULL; "tftp/rtk/cmp.b command is not supported!" are printed from a vendor helper at 0x83f153e4/0x83f15444/0x83f15580 (between `savesys` and `upgrade`), i.e. the `upgrade` family's internal `run_command` shims — so `upgrade … [TFTP]` may be non-functional while plain `tftpboot`+`bootm`, and serial `loady`+`bootm`/`go`, are compiled in. Runtime usability (net driver init, console) remains UART-gated.
3. `docs/board4-investigation.md:94`, `docs/project-reassessment.md:60`, `docs/firmware.md:26`, `docs/offline-validation.md:157` ("image magic 0x83800000 … which formats this U-Boot accepts must be checked"): statically, this loader's `bootm` does not check the magic word at all (`genimg_get_format` = `return 1`; no 0x27051956 / 0x8380xxxx / 0x9300xxxx compare in 0x83f02bf0–0x83f03708). What it does check: hcrc over the 64-byte legacy header, `ih_arch==5`, `ih_type`, `ih_comp` (LZMA 3 / gzip 1 handled; "LZMA: uncompress or overwrite error"), and dcrc when `verify` is enabled. So an OpenWrt-style header with magic 0x93000000 is not rejected by `bootm` for its magic; whether `upgrade`/flash-write paths check chip family is a separate, still-unverified path ("Loader Chip: %x" strings). The +0 field is best described as "ih_magic slot, vendor value 0x83800000, not validated by bootm" rather than "magic". Consequence: planning should focus on hcrc/arch/type/comp/load/entry and a staging address that does not overlap 0x80000000+uncompressed size; `boota` stages at 0x81000000.
4. `docs/board4-investigation.md:90` ("About 122 MiB … physical capacity/map still unverified"): add the static anchor — the stock kernel's compiled cmdline is `mem=128M` (vmlinux.bin 0x47f6cc, second copy 0x4806d8). Physical map remains unverified, but 128 MiB is the vendor's own setting, not just an inference from MemTotal.
5. `docs/board4-investigation.md:65` ("reads MTD device index 2; a runtime partition map is still needed"): the read is `mtd_read(mtd2, 0, 4096)` followed by a NUL-separated `key=value` scan for `bootmsg` (string .rodata.str1.4+0x80; parser 0x478–0x5dc), result stored at glbBoardModel+0x2a8 and returned by `sys_board_bootmsgLevel_ret`. `bootmsg=` does not occur in flash → level 2. By static registration order index 2 = SYSINFO. Not board-selection relevant; safe to close.
6. `docs/board4-investigation.md:62` ("boardMap at .data+0x160"): the symbol `boardMap` is at .data+0xc0 (nm); +0x160 is its sixth 32-byte entry. Cosmetic, but an off-by-entry error if someone decodes rows from 0x160.
7. `docs/board4-investigation.md:44/78/161`, `project-reassessment.md:63` ("PHY MDIO addresses, SerDes lanes/polarity and SFP signal polarity still need evidence"): partially recoverable statically (see §3): MDIO SMI0 addr 0–3 for mac 0/8/16/20, SDS2–5/7/8 for TE1–TE6, MOD-ABS active-low and LOS active-high as *implemented by ski.ko*. These are vendor-intent facts, not continuity tests; lane polarity/inversion is genuinely absent from the tables.
8. `docs/firmware.md:51` ("two 10G SerDes"): the profile has eight 10G lanes (SDS2–9); the OEM exposes two SFP macs (25/26 → SDS7/8); macs 24 (SDS6, 8261BE template) and 27 (SDS9) are present in the SDK profile but hidden by the OEM table. Wording should not imply only two SerDes exist.
9. `docs/firmware.md:47-48`: prints network env values (ipaddr/serverip) that the review contract treats as non-allowlisted; integrator may want to redact for consistency.
10. Duplicated-evidence note for `board4-investigation.md:49-63`: steps 1, 2 and the U-Boot-embedded profile table are the same vendor configuration; and profiles 9300034/36/37 are byte-identical at SDK level (rtcore .data+0x3434 / +0x25ac / +0x1e68). The chain is correct, but "exact profile" ≠ "exact PCB": only the OEM `portConf` row set proves the 4T2XS variant.

Nothing in the four docs was found factually wrong on port numbers, GPIO numbers, offsets 0x900/0x1f00/0x3888/0x38f0/0x2684/0x455450, payload size, load/entry, or the register-0x200 note.

## 6. What can enter an LG510S candidate definition now vs. later

Reasonable now (as *vendor-config-derived*, to be confirmed on hardware): RTL9303 (chip id 0x93036810); 128 MiB RAM intent; 16 MiB SPI NOR with the vendor map above (do not write below 0x300000); front ports TE1–TE4 = mac 0/8/16/20 on one RTL8264B at SMI0 addr 0–3 via SDS2–5; TE5/TE6 = mac 25/26 on SDS7/8, 10GBASE-R-class lane mode (raw 0x08); SFP GPIO set {SCL 8, SDA 9/10, MOD-ABS 14/17 active-low, LOS 13/16 active-high, TX_DIS 15/18 drive-low-to-enable}; reset button GPIO5; board-ID straps GPIO21–23; ADT7476 at 0x2e on SCL8/SDA11; console ttyS0 115200; stock image stages at 0x81000000, kernel load 0x80000000.
Needs more evidence before DTS/image: SerDes polarity/inversion and exact PCS mode names; whether GPIO8/9/10 should be bound as SoC hardware I²C or bit-bang; existence of the 8261BE/mac 24 and mac 27 hardware; LED wiring (sets 0x0aaa/0x0a01/0x0aa8 undecoded); reg 0x200 bit 10; DRAM geometry; UART pads/levels; runtime behaviour of `tftpboot`/`loady`/`bootm` (static presence only). No boot/flash approval implied.
